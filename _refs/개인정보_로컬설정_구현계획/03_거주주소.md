# 3. 현재 거주 주소지 (검색 API)

## 요구사항

- 텍스트 직접 입력이 아니라 **검색해서 후보 중 선택**하는 방식(API 연동)
- **좌표만 저장하고, 상세 주소 문자열은 저장하지 않는다** (사용자 확정)

## 재사용 가능한 기존 자산

통계 페이지 `commute-panel.tsx`에 이미 동일한 목적의 2단계 검색 UX가 구현되어 있다:

1. 주소 텍스트 입력 → `useGeocodeCandidates` 훅 → `/api/geocode` 호출 → 후보 목록 조회
2. 사용자가 후보 하나를 직접 클릭해 확정 (카카오 응답 1위 자동 채택 안 함 — 동/읍/면 단위
   부정확 매칭 방지 목적, `commute-panel.tsx` 주석 참고)

설정 페이지의 주소 입력도 **같은 훅·같은 API 라우트를 그대로 재사용**한다. 다만
`commute-panel.tsx`의 30초 검색 쿨다운(`commute-rate-limit.ts`)은 카카오 API 일일 쿼터
보호 목적이므로, 설정 페이지 검색에도 동일하게 적용한다.

## 저장 값 (확정)

검색 흐름 자체는 주소 텍스트/후보 라벨을 거치지만, **최종적으로 저장하는 건 좌표뿐**이다.
후보를 고르는 순간 `label`은 화면 확인용으로만 잠깐 쓰이고 저장하지 않는다.

```ts
homeCoords: { lat: number; lng: number } | null;
```

## 설정 페이지에서의 표시

주소 텍스트를 저장하지 않으므로, 저장 후에는 "정확한 주소"를 다시 보여줄 수 없다.
설정 페이지에는 좌표 유무만 표시한다.

- 저장 전: 검색창 + 후보 목록
- 저장 후: `"집 위치가 저장되어 있습니다"` + `"다시 검색"` 버튼 (기존 좌표를 지우고 재검색)

## 연동 지점

- **길찾기 자동 실행은 없다.** 지도 진입·패널 오픈 시 저장된 좌표로 알아서 검색이
  실행되는 건 한때 있었지만 제거했다(진입하자마자 패널이 자동으로 열리고 검색까지
  실행되는 게 원치 않는 동작이라는 피드백 — [08_자동화.md](08_자동화.md) 8-2 참고).
- 대신 `commute-panel.tsx`에 **"저장된 집 위치로 검색" 버튼**을 뒀다 — `savedHomeCoords`
  prop이 있고 필터 조건(`ready`)이 갖춰졌을 때만 노출되며, 눌러야만(명시적 클릭)
  좌표를 출발지로 써서 `runRanking`을 실행한다. 자동 실행과 달리 사용자가 매번
  직접 눌러야 하므로 "지도 들어가자마자/패널 열자마자 알아서 검색됨" 문제는 재발하지
  않는다.
- **지도 위 🏠 마커는 이 버튼과 별개**다 — `KakaoMap`의 `homePosition` prop은 길찾기
  패널을 열지 않아도, 검색을 한 번도 안 해도 항상 저장된 좌표에 집모양 마커를 띄운다
  (`kakao-map.tsx`, `statistics-container.tsx` 참고).
