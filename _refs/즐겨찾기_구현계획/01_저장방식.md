# 1. 저장 방식 (스토어 설계)

## 후보 두 가지 (기존 코드베이스 선례)

이 프로젝트에 로컬 저장 패턴이 이미 두 가지 있다.

**A. zustand `persist` 스토어** (`src/store/use-user-settings-store.ts`)
- `skipHydration: true` + 마운트 후 `persist.rehydrate()` 수동 호출(SSR mismatch 방지).
- 여러 컴포넌트가 구독해서 반응형으로 값을 읽는다(예: `homeCoords`는 지도·길찾기 패널
  양쪽에서 동시에 씀).

**B. 순수 localStorage 함수 + 컴포넌트 `useState` 미러링** (`src/lib/school-social-client.ts`의
`getMyRatings`/`setMyRating`)
- 서버(Supabase)에 진짜 데이터가 있고, 로컬은 "내가 뭘 했는지"만 캐싱하는 보조 역할일 때 씀.
- `statistics-container.tsx`가 `useState(getMyRatings)`로 한 번 읽고, 평가할 때마다
  `setMyRatings`로 로컬 state 갱신 + 서버 mutation을 같이 호출.

## 결정(제안): A(zustand persist) 채택, 전용 스토어로 분리

관심학교는 **서버 짝이 없는 순수 로컬 데이터**이고, 상세 패널·순위 목록·관심학교 목록
패널·필터 바(개수 표시) 등 **여러 곳에서 동시에 읽고 쓴다** — B처럼 컨테이너 하나가
소유하고 props로 내려주기엔 소비처가 너무 넓게 퍼져 있다. A가 더 적합.

**기존 `use-user-settings-store`에 필드로 얹지 않고 별도 스토어로 분리하는 이유**:
그 스토어는 `savedAt` 기준 20일 자동 만료 정책(`settings-retention.ts`)이 걸려 있는데,
관심학교는 자동으로 사라지면 기능 의미가 없다(북마크가 20일마다 날아가면 안 됨).
만료 정책이 다른 데이터를 한 스토어에 섞으면 필드별 예외 처리가 필요해져 복잡해진다 —
스토어 자체를 나누는 게 더 단순하다. 상세: [05_보존정책.md](05_보존정책.md).

## 스토어 설계 (초안)

```ts
// src/store/use-favorite-schools-store.ts
interface FavoriteSchoolsStore {
  /** schulCode 목록. 추가한 순서를 유지(최신 추가가 배열 끝) */
  favoriteCodes: string[];
  isFavorite: (schulCode: string) => boolean;
  addFavorite: (schulCode: string) => void;
  removeFavorite: (schulCode: string) => void;
  toggleFavorite: (schulCode: string) => void;
  clearFavorites: () => void;
}
```

- persist 키: `newbase-favorite-schools` (기존 `newbase-user-settings`와 별개 localStorage 키)
- `skipHydration: true` + `use-user-settings-store`와 동일하게 첫 접근 시
  `persist?.rehydrate()` 수동 호출(SSR hydration mismatch 방지 패턴 재사용)
- `favoriteCodes: string[]`을 택한 이유 — `Record<string, true>`(맵)도 가능하지만, 배열이
  "추가한 순서대로 목록 보여주기"(2차, [03_목록보기.md](03_목록보기.md))에 바로 쓰기 편하고,
  개수도 `.length`로 바로 나옴. `isFavorite` 조회는 `.includes()`로 충분(관심학교 개수가
  수백 단위로 커질 상황은 아님 — 충북 전체 학교가 524개).

## 향후 "학교 비교" 탭과의 연결 (2차, 참고만)

`favoriteCodes: string[]`는 그 자체로 "비교할 학교 코드 목록"이기도 하다 — 학교비교 탭은
이 배열을 읽어 각 코드에 해당하는 `School` 객체를 찾아 나란히 렌더하면 되므로, 이 스토어
설계를 비교 탭을 위해 따로 바꿀 필요는 없을 걸로 보인다(스토어는 1차 그대로 두고 소비하는
쪽만 2차에서 늘어나는 구조). 단, 비교 UI에 "한 번에 비교할 수 있는 최대 개수" 제한이
필요해지면 그건 스토어가 아니라 비교 탭 컴포넌트 쪽에서 처리하는 게 맞다(관심학교 자체는
계속 몇 개든 저장할 수 있어야 하므로).

## 개인정보 원칙과의 관계

CLAUDE.md의 "개인정보 보호 원칙(불변조건)"은 NEIS 인사기록카드(경력·포상 등 식별 정보)
대상이다. 관심학교는 학교 코드 목록일 뿐이라 그 불변조건이 막는 대상은 아니지만,
"서버로 보내지 않는다"는 방향성은 동일하게 유지한다 — 이 스토어도 순수 클라이언트
전용이며 어떤 API 라우트와도 연결하지 않는다.
