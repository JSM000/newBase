# 학교 통계 지도 기능 구현 계획

> 목표: 전보를 고려하는 교사가 지도에서 학교를 선택해 그 학교의 참고 통계(점수 산정 관련 + 근무 난이도·편의성)를 확인할 수 있게 한다.
> 데이터 소스: 학교알리미 OpenAPI (`_refs/학교알리미_OpenAPI_출력값.xlsx` 참고, API 키 보유)
> 지도 렌더링: 카카오맵 JavaScript SDK

---

## 1. 범위

- **지역**: 충청북도 전역만 (확정 — 전국 확장 없음)
- **학교급**: 유치원 + 초등학교 + 중학교 + 고등학교 전체
- **설립구분**: 공립 우선 (사립 포함 여부는 추후 결정)

---

## 3. 아키텍처

### 3-1. 데이터 수집 파이프라인 (배치, 런타임 API 호출 없음)

- 학교알리미 OpenAPI를 배치 스크립트(`scripts/collect-school-stats.mjs`)로 호출해 충북 유·초·중·고 전체 학교의 채택 항목(2-1, 2-2)을 수집
- 요청 URL은 전 엔드포인트 공통 `http://www.schoolinfo.go.kr/openApi.do`이며 `apiType` 값만 바뀜(시트명 괄호 번호와 대응, 예: 학교기본정보=0, 학교 현황=62, 직위별 교원 현황=22). 공통 필수 파라미터는 `apiKey`, `apiType`, `schulKndCode`, `sggCode`(문서엔 "선택"으로 표기되어 있었으나 실제 호출 시 필수 확인됨) — 학교급(02 초등/03 중등/04 고등) × 충북 14개 시군구(`_refs/시도시군구코드.xlsx`)를 전부 순회해서 호출
- **엔드포인트마다 필수 파라미터가 다를 수 있음** — 학교 현황(62)·직위별 교원 현황(22)은 위 공통 파라미터에 더해 `pbanYr`(공시연도, NUMBER 필수, 최근 3년치만 제공)도 필수. 학교기본정보(0)는 `pbanYr` 없이 호출됨. 새 엔드포인트 추가 시 해당 API 문서의 요청인자 표를 매번 확인해야 함. 스크립트는 pbanYr을 최신 연도부터 자동 후보 탐색해서 사용
- `SCHUL_CODE`(정보공시 학교코드)를 키로 여러 시트(엔드포인트) 응답을 **평탄한(flat) 객체로 병합** — 시트별로 중첩 저장하지 않음. 지표 선택 UI(3-3)가 `school[선택한key]`로 바로 접근할 수 있어야 하기 때문. 시트 간 동명 필드(예: 여러 시트에 있는 "학급수계", "총 교원수") 충돌은 시트마다 의미가 드러나는 고유 camelCase 키로 정규화해서 회피(예: 학교현황의 학급수계 → `homeroomClassCount`, 직위별교원현황의 총교원수 → `teacherCountTotal`)
- **원본 API 필드명 → 저장 필드명 매핑도 데이터 파일에 그대로 실음** — 별도 매핑 파일을 만들면 코드(`normalize()`)와 매핑 파일이 따로 놀다 어긋날 위험이 있어서, 대신 `DATASETS` 설정 안에 `fieldSource`(예: `{ homeroomClassCount: "COL_SUM" }`, 여러 필드를 합친 경우는 배열)를 선언해두고 이걸 그대로 `source.datasets[].fieldSource`로 출력. 나중에 저장된 필드명이 헷갈리면 스크립트 코드를 안 열어봐도 데이터 파일만 보고 원본 API 필드명을 확인 가능
- 결과를 정적 JSON으로 저장: **`public/data/chungbuk-schools.json`** (src/data가 아님 — 3-4 참고)
- 학교기본정보(0)에 없는 학교(예: "OO중학교부설방송통신중학교" 같은 부설·겸임 기관 — 학교현황(62)엔 학급/학생 통계가 있지만 직위별교원현황(22)엔 자체 교원 정원이 없어 본교 교사가 겸임하는 구조로 추정됨)는 최종 결과에서 제외. 전보 대상 근무지가 아니라고 판단
- **공시제외(PBAN_EXCP_YN="Y") 행은 "값 0/없음"이 아니라 "학교가 해당 항목 자체를 입력하지 않아 제외됨"** — 모든 시트에 공통으로 있는 필드. 실측: 용암초등학교의 지원시설현황(18) 응답에 `PBAN_EXCP_YN: "Y"`, `PBAN_EXCP_RSN: "본교는 해당항목에 대해서 교육통계 입력자료가 없으므로 제외함."`. 특히 값이 0이면 API가 키 자체를 생략하는 필드(교사현황17의 교원지원공간, 지원시설현황18의 체육관·강당)는 "공시제외"와 "진짜 0"이 똑같이 키 생략으로 보여서 구분이 안 됐었는데, 이 필드로 구분해서 공시제외 행은 병합 자체를 건너뛰어(null로 남김) 해결
- **공시제외 사유를 데이터에 그대로 저장** — 화면에서 "이 학교는 왜 이 데이터가 없는지" 보여줄 수 있도록, 데이터셋마다 `<필드>ExcludedReason`(예: `facilitiesExcludedReason`, `schoolStatusExcludedReason`) 필드에 `PBAN_EXCP_RSN` 원문을 그대로 저장. 전수조사 결과 사유가 12종으로 다양함 — 단순 "입력자료 없음" 외에 "본교통합작성"(분교 데이터가 본교 수치에 합산됨), "통합운영학교로서 OO중학교에서 처리 함"(초·중이 캠퍼스를 같이 써서 시설 데이터가 페어 학교 쪽에만 있음), "해당 학교는 지원시설이 없으므로 제외처리 함"(사실상 확정된 0인데 제외로 표현됨) 등 — UI에서 이 원문을 그대로 노출하면 사용자가 맥락을 알 수 있음
  - 44(대장 6종)/24-중고(과목별)처럼 학교당 여러 행이 나오는 데이터셋은 행마다 제외 사유가 다를 수 있어서, 마지막 사유로 덮어쓰지 않고 **서로 다른 사유를 전부 "/"로 이어붙여 보관**(중복 제거)
- **"값 0이면 키 생략" 여부는 데이터셋마다 다름 — 매번 실측 필요** — 교사현황(17)/지원시설현황(18)은 값이 0이면 키 자체가 빠지는데, 표시과목별 교원 현황(24, 초등부)은 반대로 값이 0이어도 키가 항상 옴(`scripts/check-key-presence.mjs COL_9 24 02 10`로 확인: 264행 전부 키 있음, 그중 256행이 명시적 0). 그래서 24번은 `?? 0` 없이 `toNumberOrNull` 그대로 써도 안전함. 새 필드를 추가할 때마다 이 스크립트로 먼저 확인하고 `?? 0` 필요 여부를 정할 것
  - **"이 데이터 필드가 null이면 어느 ExcludedReason 필드를 봐야 하는가"는 데이터 필드마다 1:1로 정해져 있음** (예: `auditoriumCount`/`gymnasiumCount` → `facilitiesExcludedReason`, `specialistSubjectTeacherEstimate` → `subjectTeacherExcludedReason` — 서로 다른 데이터셋이라 처음부터 다른 필드에 저장되므로 "여러 사유 중 뭘 골라야 하는지" 헷갈릴 일이 없음). 다만 이 대응관계가 수집 스크립트(`collect-school-stats.mjs`의 `DATASETS` 배열) 안에만 있으면 프론트가 알 방법이 없으므로, 출력 JSON의 `source.datasets[].fields`/`excludedReasonField`에 그대로 실어서 **데이터 파일만 보고도 "이 필드 → 이 reason 필드"를 찾을 수 있게** 함
- **여러 데이터셋이 병합된 뒤에만 계산 가능한 파생 필드는 `DERIVED_FIELDS`로 별도 관리** — `transferChurnRate`(전입출비율)·`supportStaffCount`(행정지원인력)·`scholarshipSupportRate`(장학지원비율) 3개는 서로 다른 API(학교현황62/전출입10/직원68/장학55) 필드를 조합한 계산값이라 특정 dataset의 `normalize()` 안에서 못 만들고, 전체 병합이 끝난 뒤 한 번에 계산해서 필드로 저장. 프론트(`school-indicators.ts`)는 이 필드를 그대로 읽기만 해서, **계산식이 스크립트 한 곳에만 존재**(지도/클러스터 집계 양쪽에 복제 안 함). 출력 JSON의 `source.derivedFields`에 메타데이터로 노출(어느 필드들을 조합했는지)
- **지도 클러스터링용 소속명(`sigunguName`/`subRegionName`)도 같은 이유로 `DERIVED_FIELDS`에 포함** — 원래는 `adrcdNm`/`address` 문자열을 프론트(`school-region.ts`)와 클러스터 집계 스크립트(`build-school-clusters.mjs`) 양쪽에서 각자 정규식으로 파싱하고 있었음(필터/줌 전환마다 반복 파싱 + 로직 2곳 복제). 파싱 결과를 학교 데이터에 필드로 미리 박아둬서, 양쪽 다 필드만 읽도록 정리(파싱 로직은 `collect-school-stats.mjs` 한 곳에만 존재)


- 갱신 주기: 학교알리미 공시 주기(연 1~2회)에 맞춰 스크립트 수동 재실행 (기존 인사계획 PDF/지도 데이터와 동일한 "사전 수집" 철학)

**데이터 파이프라인 계층 분리 (구현 완료)**

수집 스크립트가 늘어날 걸 대비해(연구학교 등 다른 출처 병합 예정 — 4번 참고), 원본 보전과 프론트 최적화를 단계로 분리함:

| 단계 | 스크립트 | 산출물 | 역할 |
|---|---|---|---|
| ① 수집 | `collect-school-stats.mjs` | `public/data/chungbuk-schools.json` | 학교알리미 API 원본을 **최대한 보전**해서 병합 (pretty-print, `source` 메타 포함) — 사람이 읽고 디버깅하는 용도, 필드 추가/삭제는 최소한으로 |
| ② 최적화 | `build-schools-dataset.mjs` | `public/data/chungbuk-schools-render.json` | ①을 읽어서 **프론트가 실제로 fetch하는 모양**으로 정리 — 안 쓰는 필드/`source` 메타 제거, 압축(minify) 저장 |
| ③ 클러스터 집계 | `build-school-clusters.mjs` | `public/data/chungbuk-school-clusters.json` | ②를 읽어서 지도 클러스터 위치(`bestCenter`)만 사전 계산 (3-2 참고) |

- ①은 API 응답을 그대로 옮기는 역할에 집중 — 나중에 연구학교 등 다른 출처를 추가할 때도 **출처별로 수집 스크립트를 따로 둠**(`collect-school-stats.mjs`는 학교알리미 전용으로 그대로 두고, 연구학교용 수집 스크립트를 별도로 만드는 식)
- ②가 "여러 출처를 하나로 합쳐서 프론트에 줄 최종 데이터셋을 만드는" 지점 — 연구학교 데이터를 merge하게 되면 이 스크립트에 "다른 원본 읽기 → `schulNm` 등으로 매칭 → merge" 단계를 추가할 예정 (아직 미구현, 연구학교 자체를 나중에 하기로 함 — 4번 참고)
- ②에서 제거하는 필드(프론트 어디서도 안 읽는 걸 grep으로 확인): `detailAddress`, `zipCode`, `tel`, `homepage`, `isSuspended`, `isBranchSchool`, `isClosed`, `lctnScCode`, `sidoOfficeNm`, `source`(전체) — `src/types/school-stats.ts`의 `School` 타입도 이 모양(render 파일 기준)으로 맞춰 트리밍함. 원본처럼 pretty-print로 저장(사람이 열어보고 확인하는 일이 많아서 — gzip 압축 시 minify 대비 차이는 ~15%뿐이라 가독성을 택함)
- `schulKndNm`(예: "초등학교")도 `schulKndCode`(02/03/04)와 1:1 중복이라 ②에서 제거 — 프론트는 필요하면 기존 `SCHOOL_LEVEL_OPTIONS`(`school-region.ts`)로 유도(`school-detail-panel.tsx`의 `schulKndLabel()`)
- 좌표(`position.lat/lng`)는 소수점 6자리(약 11cm 정밀도)로 반올림해서 저장 — 원본은 소수 10자리 이상인데, 좌표는 학교마다 사실상 랜덤한 숫자열이라 반복 문자열과 달리 gzip이 못 줄여줘서 실측으로도 효과가 있었음(아래 크기 참고). `chungbuk-school-clusters.json`의 `bestCenter`(평균 계산값이라 부동소수점 오차로 소수 15자리 이상 나옴)도 동일하게 반올림
- 파일 크기(반올림 적용 후): render 파일 raw 1.51MB(원본 1.69MB), gzip 101KB(원본 123KB) / clusters 파일 gzip 2.7KB
- `npm run collect:schools` → `npm run build:dataset` → `npm run build:clusters` 순서로 실행 (재수집할 때마다 3개 다 재실행) — 한 번에 묶은 `npm run build:all`도 있음(`SCHOOLINFO_API_KEY=발급받은키 npm run build:all`)

### 3-2. 지도 렌더링 (카카오맵)

**설계 원칙: 카카오 API 호출 최소화**
- Kakao Maps JavaScript SDK를 **지도 최초 렌더링 시 1회만** 스크립트 로드 (appkey 사용)
- 이후 마커 생성·hover 툴팁·click 상세 패널은 전부 **3-1에서 이미 수집해둔 정적 데이터**로 클라이언트에서 렌더링 — 추가 API 호출 없음
- Geocoding·장소검색 등 다른 카카오 API는 사용하지 않음 (위경도는 학교알리미가 이미 제공하므로 좌표 변환 자체가 불필요)

**마커 클러스터링 — 행정구역 기반 3단계 (구현 완료, Kakao 표준 `MarkerClusterer` 대체)**
- Kakao Maps SDK 표준 `MarkerClusterer`는 화면 픽셀 거리로만 묶어서 행정구역 개념이 없음(줌 레벨 안에서도 같은 시군구가 여러 클러스터로 쪼개지거나, 다른 시군구가 한 클러스터로 섞일 수 있음) — 그래서 안 쓰고, `CustomOverlay`로 직접 구현
- 줌 레벨(숫자 클수록 축소)에 따라 3단계로 전환 (`kakao-map.tsx`):
  | 레벨 | 표시 |
  |---|---|
  | 9 이상 | 시·군 11개 클러스터 |
  | 6~8 | 구/읍/면/동 클러스터 |
  | 5 이하 | 개별 학교 마커 |
- 구분 판별: **학교 데이터의 `sigunguName`/`subRegionName` 필드를 그대로 읽음** (원래는 매 렌더마다 `adrcdNm`/`address`를 정규식으로 파싱했었는데, 필터/줌 전환마다 반복되는 게 불필요해서 `collect-school-stats.mjs`의 `DERIVED_FIELDS`로 옮겨 한 번만 계산해두는 것으로 최적화함 — 3-1 참고). `src/lib/school-region.ts`는 이 필드를 읽어 그룹핑만 함
  - `sigunguName`: `adrcdNm`에서 "시/군"으로 끝나는 토큰. 청주시는 하위 구를 구분 안 하고 "청주시"로 통일
  - `subRegionName`: `adrcdNm`에 구가 있으면(청주시) 그 구를 최우선 사용, 없으면(그 외 시/군) `address`(지번주소)의 3번째 토큰 사용. **주의**: `address`는 일부 학교(2014년 청주시-청원군 통합 이전 옛 지명 "청원군"이 안 고쳐진 11건)가 최신이 아니라서, 항상 최신인 `adrcdNm`을 우선 신뢰해야 함 — 실제로 이 버그가 있었고 수정함
- 클러스터 클릭 시: `bestCenter`(아래 참고)로 `setCenter` + 다음 단계 레벨로 `setLevel` (뱃지 표시 위치와 이동 위치가 같은 값이라 별도 bounds 계산이 필요 없음 — 초기엔 그룹 전체 bounds로 `setBounds`했었는데, 청주시처럼 넓게 퍼진 그룹은 bounds fit만으론 다음 단계로 안 넘어가서 강제 확대까지 따로 처리해야 했음. bestCenter 연결 후 더 단순해짐)

**클러스터 마커가 찍히는/이동하는 위치 — "밀집 위치" 탐색 (구현 완료)**
- 그룹 전체의 단순 평균 좌표를 쓰면, 학교들이 한쪽에 몰려있고 1~2개가 멀리 떨어진 경우 평균이 빈 공간에 찍히는 문제가 있었음
- **뱃지 표시 위치 = 클릭 시 이동 위치, 하나로 통일** (따로 안 나눔)
- 알고리즘: 그룹 안 학교마다 "반경 R km 안에 이웃이 몇 개인지"(하버사인 거리) 세서, 제일 많은 후보를 찾고, 그 후보+이웃들의 평균 좌표를 최종 위치로 사용. 그룹당 N개 학교면 N×N 비교(제일 큰 그룹 57개도 3,249번 — 연산 부담 없음)
- R은 티어마다 다름: 시·군 클러스터는 5km(다음 단계인 구/읍/면/동 스케일), 구/읍/면/동 클러스터는 2km(다음 단계인 개별 학교 스케일) — 실제 화면 보고 조정 가능한 상수

**클러스터 집계 데이터 — 별도 파일로 사전 계산, "밀집 위치"만 저장 (구현 완료, 프론트 연결 완료)**
- 처음엔 개수·지표평균(색상)까지 다 미리 계산해서 저장하려 했었으나(학교급×공립여부×13지표 조합), 재검토 후 **"밀집 위치"만 저장**하는 것으로 단순화함. 판단 기준: *① 필터에 따라 값이 안 바뀌고, ② 다른 계산(그룹핑)의 부산물이 아니라 별도 계산이 필요한 경우에만* 미리 저장할 가치가 있음
  - 개수/지표평균: 학교급·공립여부·검색어·선택된지표에 따라 매번 달라지고, 어차피 검색어 처리 때문에 클라이언트에서 학교 목록을 그룹핑해야 하니(`groupSchoolsBySigungu`/`groupSchoolsBySubRegion`) 그 결과에서 개수(`.length`)·평균값이 공짜로 나옴 → 저장 안 함, 그때그때 계산
  - 밀집 위치: 그룹의 지리적 구성(배치 재수집 때만 바뀜)에만 좌우되고 필터와 무관, 반경 탐색이라는 별도 알고리즘이 필요 → **저장함**
- 학교 데이터와는 별도 파일 `public/data/chungbuk-school-clusters.json`으로 저장(`scripts/build-school-clusters.mjs`, `npm run build:clusters`). API 호출 없이 `chungbuk-schools-render.json`만 읽어서 만듦(파이프라인 ③단계, 3-1 참고) — 프론트 줌 레벨/반경 상수를 튜닝해도 API 재호출 없이 이 스크립트만 재실행하면 됨
- 그룹(시·군 11개, 구/읍/면/동 120개)마다 `{ name, bestCenter }`만 저장(구/읍/면/동은 `sigungu`도 같이). `bestCenter`가 null인 그룹(소속 학교가 전부 좌표 없음/폐교, 실측 1건: 보은군 내북면)은 결과에서 제외
- 파일 크기 실측: raw 20KB, gzip 2.7KB (개수·지표평균 다 넣었을 때는 raw 734KB, gzip 35.5KB였음 — 그것도 부담 없는 크기였지만, 굳이 저장할 필요가 없어서 더 줄임)
- 검색어 필터 처리 방침: 자유 텍스트라 미리 계산도 그룹핑 재사용도 불가능 → 검색 중엔 클러스터 뷰 무시하고 개별 마커를 줌 레벨과 무관하게 바로 표시 **(아직 미구현 — 별개 작업, `bestCenter` 연결과 무관하게 남아있음)**
- **프론트 연결 (구현 완료)**: `kakao-map.tsx`가 `useSchoolClusters()`(`src/hooks/use-school-clusters.ts`)로 이 파일을 fetch해서 그룹 이름(시·군은 `name`, 구/읍/면/동은 `sigungu|name`)으로 `bestCenter`를 찾아 뱃지 위치 + 클릭 시 이동 위치로 사용. 아직 못 불러왔거나 매칭이 안 되는 경우에만 `school-region.ts`의 단순 평균(`group.center`)으로 대체(fallback)

**표시 지표 선택 (범례 연동)**
- "표시할 통계" 선택 UI(드롭다운)로 2-1·2-2에서 채택한 지표 중 지도에 시각화할 값을 사용자가 고름 (예: 학생수, 학급당학생수, 교사 1인당 학생수 등 구간을 나눌 수 있는 수치형 지표)
- 선택한 지표 값에 따라 마커 색상/크기를 구간별로 다르게 표시 (예: 학생수 100명 미만/100~300/300~600/600 이상 4단계)
- 화면 한쪽에 현재 선택된 지표의 구간-색상 매핑을 보여주는 **범례** 표시
- 지표별 구간 기준(bucket 경계값)은 구현 단계에서 지표마다 별도 정의 필요 (지표마다 값 분포가 다름)

**지도 (중앙)**
- 카카오 지도 + 클러스터링 마커 (학교급별 아이콘/색상 또는 선택된 지표 기준 색상 중 택1 — 동시 표현 방식은 구현 단계 결정)
- hover: 학교명 + 핵심 지표 미니 툴팁
- click: 상세 패널(사이드시트) — 2-1(점수 참고) / 2-2(근무여건 참고) 두 섹션으로 구분. 이 구분은 **저장 구조가 아니라 프론트엔드 표시 단계**에서 "이 키들은 점수참고, 이 키들은 근무여건참고"로 매핑해서 처리 (3-1의 flat 저장 구조와 모순되지 않음)

**학교 순위 목록 (신규 기능, 계획 단계 — 미구현)**

필터를 걸어둔 상태에서 현재 "표시 지표" 기준으로 학교를 오름차순/내림차순 정렬해서 오른쪽 사이드바에 목록으로 보여주는 기능.

- **순위 기준 = "표시 지표" 드롭다운과 동일** — 지도 색칠에 쓰는 지표를 그대로 순위 기준으로 재사용. 별도의 "순위용 지표" 선택 UI는 만들지 않음 (선택지 하나로 지도 색상과 순위 기준이 항상 일치해서 혼란이 없음)
- **진입점**: `SchoolFilterBar`의 "표시 지표" 드롭다운 옆에 **"순위 보기" 버튼** 추가
- **대상 목록**: 현재 적용된 필터(학교급/시군/검색어/공립여부, `statistics-container.tsx`의 `filtered`)를 그대로 재사용 — 지도에 보이는 학교와 순위 목록의 학교가 항상 일치함(별도로 다시 필터링하지 않음)
- **정렬**:
  - 대상: `filtered` 중 `indicator.accessor(s) !== null`인 학교만 번호(1, 2, 3…)를 매겨 정렬
  - 값이 같으면 학교명 가나다순으로 2차 정렬(안정적인 순서 보장)
  - 지표 값이 없는(`자료 없음`) 학교는 순위에서 제외하고, 목록 맨 아래에 "OO개 학교는 자료 없음" 안내만 표시(기존 `IndicatorLegend`의 `noDataCount`와 같은 맥락)
  - 오름차순/내림차순 토글은 순위 패널 헤더에 위치(기본값: 내림차순 = 높은 값 먼저)
- **필터를 바꾸면 목록도 즉시 갱신** — 순위 버튼을 다시 누를 필요 없이 `filtered`가 바뀌면 정렬도 다시 계산(하나의 `useMemo`)
- **패널 동작**: 기존 학교 상세 패널과 같은 자리(오른쪽 사이드바)를 공유 — 아래처럼 셋 중 하나만 보이는 상태로 관리
  - `panelMode: 'none' | 'ranking' | 'detail'` (가칭) — "순위 보기" 클릭 시 `'ranking'`, 목록 항목 또는 지도 마커 클릭 시 `'detail'`(+ `selected` 학교 설정), 어느 쪽이든 닫기(X) 누르면 `'none'`
  - 순위 목록에서 학교를 클릭하면 **기존 상세 패널로 전환**(순위 목록은 사라짐). 상세 패널을 닫으면 순위 목록으로 자동 복귀하지 않고 지도만 보임 — 다시 보려면 "순위 보기"를 재클릭 (모드가 뒤로가기 스택이 아니라 단순 3-상태라 구현이 쉬움)
- **목록 항목 구성**: 순위 번호, 학교명, 소속(시·군 · 구/읍/면/동 — `sigunguName`/`subRegionName` 그대로 사용), 지표 값(단위 포함). 클릭 시 상세 패널 전환 + 지도도 해당 학교 위치로 이동(마커 클릭과 동일 동작)
- **성능**: 524건 규모에서 정렬은 `O(n log n)` 한 번으로 충분히 가벼움 — 가상 스크롤(virtualization) 등 별도 최적화 불필요, 그냥 스크롤 가능한 목록으로 구현

### 3-4. 데이터 전달 방식

- 병합 결과 JSON은 `src/data/`가 아니라 **`public/data/`**에 둔다. `src/data/`에 두고 `import`하면 웹팩이 JS 번들에 그대로 포함시켜서, 지도 페이지를 방문하지 않는 사용자에게도 번들 용량이 묻어갈 위험이 있음
- 프론트가 실제로 fetch하는 건 원본이 아니라 **최적화 산출물 `public/data/chungbuk-schools-render.json`**(위 파이프라인 ② 단계) — `/statistics` 페이지가 마운트될 때 클라이언트에서 `fetch('/data/chungbuk-schools-render.json')`로 받아온다(`use-chungbuk-schools.ts`). 정적 파일이라 (a) 지도 페이지를 실제 방문한 사용자만 받고, (b) JS 번들과 분리되어 브라우저가 별도로 캐싱하므로 재방문 시 재다운로드 없음, (c) Next의 정적 파일 서빙 압축 혜택을 받음
- 참고: render 파일 실측 1.15MB(524개 학교, minify 기준)/gzip 90KB — 정적 파일 1회 fetch로 충분히 감당 가능한 크기. DB 도입이나 서버사이드 페이지네이션 없이 이 방식으로 진행
